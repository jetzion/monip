# MONIP Group Website Rebuild --- Implementation Plan

**Document:** `PLAN.md`\
**Status:** In progress --- core site built and tested locally;
deployment on hold (last updated 2026-10-24)\
**Companion documents:** `REQUIREMENTS.md`, `CLAUDE.md`, `README.md`,
`Editor_guide_for_MONIP.md`

## 1. Objective

Deliver a modern, responsive, multi-page MONIP Group website using a
custom Next.js frontend and Payload CMS, deployed through
Vercel. The site must provide an easy-to-maintain corporate presence and
a CMS-driven product catalog.

Use `REQUIREMENTS.md` as the functional source of truth. If
implementation reveals a conflict or missing decision, document it and
ask for clarification rather than silently inventing business
requirements.

## 2. Architecture

### Core stack

-   **Next.js 16.4** with App Router; `cacheComponents` disabled because
    Payload does not guarantee full compatibility.
-   **TypeScript** with strict type checking.
-   **Payload CMS 3.91** running inside the Next.js app, admin panel at
    `/admin`. Content is read through Payload's Local API on the server
    with `overrideAccess: false`, so collection access rules always apply.
-   **Postgres**: Docker locally, Neon in production. Schema changes ship
    as migrations in `migrations/`.
-   **Media storage**: local disk in development, Vercel Blob (client
    uploads) in production.
-   **Publishing**: Payload drafts with autosave. Collection hooks call
    `revalidatePath` only when a save changes public content (publish or
    unpublish), not on draft autosaves.
-   **Live Preview**: `/preview` enables Next.js draft mode for logged-in
    Payload users only; drafts are then queried as that user.
-   **Vercel** for preview and production deployment.
-   **Tailwind CSS v4 + shadcn/ui** with design tokens; the visual
    direction is clean and business-professional.
-   **Resend** (via `@payloadcms/email-resend`) for notification and
    auto-reply email.
-   **Vitest** for unit/component tests and **Playwright** for
    end-to-end tests.
-   **pnpm** as the package manager.
-   **Vercel Observability and runtime logs** for basic monitoring.
-   **OpenRouter** (OpenAI-compatible Chat Completions) for the website
    chat, called only from the server route `POST /api/chat`, and for the
    admin "Write description with AI" button (`POST /api/products/describe`,
    logged-in editors only).

### Architectural principles

-   Keep the frontend decoupled from CMS presentation templates.
-   Use reusable page templates and components.
-   Fetch public content through narrowly scoped, read-only queries.
-   Use static generation or server rendering where appropriate.
-   Use draft/preview mode only through protected server-side routes.
-   Keep secrets and privileged tokens server-side.
-   Use stable slugs and preserve URL continuity where possible.
-   Payload's Postgres database and admin logins are approved; avoid
    other databases, public authentication, or integrations without an
    approved requirement.

## 4. Data Model

Built: Product, Product Category, Service, Client, Office, Success Story,
Page, Home (global), Inquiry, Users, Media. Not built yet: Site Settings
(waiting for approved content). Success Stories replaced the planned
Case Study model (2026-10-24).

### Product

-   `name` --- required.
-   `slug` --- required and unique.
-   `summary` --- required for cards and previews.
-   `description` --- rich text or structured content.
-   `primaryImage` --- required for publication.
-   `gallery` --- ordered list of uploads; alt text lives on each Media item.
-   `category` --- required reference to a category.
-   `subcategory` --- optional reference to a category whose parent is
    the selected category.
-   `tags` --- optional.
-   `materials` --- optional list.
-   `customizationOptions` --- optional list.
-   `applications` --- optional list.
-   `specifications` --- optional label/value rows (public only).
-   `featured` --- boolean.
-   `labels` --- optional, controlled values.
-   `seo.title` and `seo.description` --- optional with sensible
    fallbacks.
-   Status --- use Payload drafts (`_status`: draft/published) only.
    "Archive" means unpublish; no separate status field.
-   `publishedAt` --- set or maintain consistently.
-   Duplicating (admin "Duplicate") creates a draft named "... (copy)"
    with the next free slug (`-copy`, `-copy-2`, ...), not featured and
    with no `publishedAt`.

Do not store supplier details, internal cost, internal notes, or other
confidential information in the CMS at all. Do not expose pricing or
lead-time information unless MONIP explicitly approves it.

### Product Category

-   `title`, `slug`, `description`, `image` (optional), `parent`
    (optional reference; set for subcategories), `sortOrder`,
    `seo.title`, `seo.description`.

### Service

-   `title`, `slug`, `summary`, `body`, `image` (optional), `sortOrder`;
    drafts. Shown as sections on `/services` (no detail pages yet).

### Home (global)

-   `hero` (headline, intro, about link label) and `closing`
    (heading, button label); drafts and Live Preview. Link targets are in code.

### Client

-   `name`, `logo` (required upload); drafts; `orderable` (drag-and-drop
    order stored in `_order`, fractional index; replaced `sortOrder`). Shown as a logo grid
    on `/clients` under the "Our clients" page title and intro.

### Office

-   `name`, `address` (optional), `latitude`, `longitude`, `sortOrder`;
    drafts. Shown on About as pins on `public/world-map.svg` (Natural
    Earth 1:110m land, public domain; equirectangular, lat 84 to -58,
    projection in `lib/offices-map.ts`) and as a list. Also in the chat
    knowledge.

### Page

-   `title`, `key` (unique: about, products, clients, success-stories,
    privacy), `intro`, `image` (optional), `body`, SEO fields; drafts.
    Each key maps to a route in code. The products and success-stories
    entries only supply the page header.
-   A page, `/services`, and their nav links appear only when published
    content exists; otherwise the route returns 404. `/products` always
    renders, with or without its Pages entry.

### Success Story

-   `title`, `slug`, `publicationDate` (optional), `summary`,
    `featuredImage` (required), `body`, `gallery`, `industry`
    (optional), `customerName` (shown only when `customerApproved` is
    ticked), SEO fields; drafts and `orderable`. Shown on
    `/success-stories` and at `/success-stories/<slug>`; details in
    section 15.

### Site Settings (Payload global, not built)

The logo is a static file in code (`public/monip-logo.png`). Footer
content and contact details wait for approved content.


-   Approved logo and brand assets.
-   Navigation configuration if appropriate.
-   Footer content.
-   Approved contact information.
-   Default SEO metadata and social image.

### Inquiry

Written only by the server-side form handler; never queried by public
pages.

-   `type` --- general or product.
-   `name`, `email`, `company` (optional), `phone` (optional),
    `message`.
-   `product` --- reference to the product, plus the product name and URL
    captured at submission time.
-   `createdAt` (submission time, set by Payload).
-   `emailStatus` --- whether the notification email was accepted.

### Users

Payload auth collection for admin panel logins, with `admin` and
`editor` roles. The first account becomes admin; only admins can set
roles.

### Access control

-   Public reads return published Products, Services, Clients, Offices,
    Success Stories, Pages, and the published Home global only;
    Categories (no drafts) are always public.
-   Drafts are visible only to logged-in users, including in Live Preview.
-   Inquiries contain personal information: no public read or create,
    no updates by anyone, readable and deletable only by admins. The form
    handler creates them via the Local API on the server.
-   Editors manage content; only admins manage users and read inquiries
    (open question in the editor guide: should editors see inquiries?).

Avoid making every text fragment editable through the CMS. Make business
content editable while keeping structural layout and reusable UI
controlled in code.

## 5. Phased Work Plan

### Approved build order (vertical slice first)

The phases below group the scope. Implementation follows this order:

1.  Minimal shell: design tokens, header, footer, base components.
2.  Product and Category collections in the Payload admin.
3.  Catalog page, product detail page, Live Preview, on-publish
    revalidation.
4.  Product inquiry: save to Payload, notify MONIP, auto-reply,
    success/error states.
5.  Home (with featured products), About, Services, Contact, reusing
    established patterns.
6.  Search and filters, SEO, sitemap, remaining pages.

A few clearly marked placeholder products may be created in Payload for
development; MONIP replaces them through manual entry.

### Phase 0 --- Repository and environment inspection

1.  Inspect the existing repository, package manager, framework,
    branches, and current deployment.
2.  Identify existing brand assets, fonts, images, copy, and any useful
    components.
3.  Inventory current website URLs and content that may need migration.
4.  Identify the current domain/DNS owner and required access.
5.  Confirm Node.js version and deployment constraints.
6.  Record unknowns in a decision log.
7.  Do not delete or replace existing files before understanding their
    purpose.

**Deliverable:** Repository assessment, content inventory, environment
checklist, and decision log.

### Phase 1 --- Requirements and design foundation

1.  Validate `REQUIREMENTS.md` with MONIP.
2.  Confirm primary audience, key messages, calls to action, product
    categories, and contact workflow.
3.  Establish brand tokens: colors, typography, spacing, layout widths,
    image ratios, and interaction states.
4.  Define sitemap, responsive navigation, footer, and reusable page
    templates.
5.  Create or implement a small set of representative layouts before
    building every page.
6.  Verify that the design direction works for real MONIP assets.

**Deliverable:** Approved design direction and shared layout/component
foundation.

### Phase 2 --- Project setup and Payload configuration

1.  Configure Next.js App Router and TypeScript strict mode.
2.  Set up formatting, linting, environment validation, and test
    commands.
3.  Install Payload, configure Postgres, and set up the admin panel.
4.  Implement schemas for products, categories, services, success
    stories, and site settings.
5.  Add required-field validation, slug rules, image guidance, and
    editor-friendly field groups.
6.  Implement reusable Local API queries with generated Payload types.
7.  Configure drafts and Live Preview securely.
8.  Document required environment variables without committing actual
    secrets.

**Deliverable:** Working CMS with sample content and a documented local
setup.

### Phase 3 --- Shared site shell and core pages

Build in this order:

1.  Global typography, colors, spacing, buttons, cards, and form
    components.
2.  Header, desktop/mobile navigation, and footer.
3.  Homepage.
4.  About page.
5.  Services page.
6.  Sustainability page: removed 2026-10-23 at MONIP's request.
7.  Clients page (`/clients`: Pages "Our clients" for title and intro, `clients` collection for logos). Projects are shown as Success Stories.
8.  Contact page and privacy page.
9.  Not-found page and error states.

All page content should use approved content or clearly identified
temporary development fixtures. Do not invent MONIP facts, clients,
metrics, certifications, or testimonials.

**Deliverable:** Responsive corporate site shell and content pages.

### Phase 4 --- Product catalog

1.  Implement catalog page and category navigation.
2.  Add server-side product retrieval for published content.
3.  Build product cards and responsive image handling.
4.  Implement agreed search and filters.
5.  Build product detail pages from a reusable template.
6.  Add featured products to the homepage.
7.  Add related products only where useful and data supports it.
8.  Implement product-specific inquiry forms.
9.  Handle invalid slugs, empty categories, no search results, and
    unpublished products.
10. Confirm that archived/draft items do not leak into public pages,
    search, or sitemap.

**Deliverable:** Fully CMS-driven public catalog and product detail
pages.

### Phase 5 --- Inquiry delivery

1.  Confirm MONIP's approved inquiry recipient and delivery provider.
2.  Define form fields and privacy notice.
3.  Add client-side usability validation and server-side schema
    validation.
4.  Add spam mitigation and rate limiting appropriate to the deployment.
5.  Deliver the submission through a server-side integration.
6.  Include product name and URL in product-specific inquiries.
7.  Add clear success, validation, and failure states.
8.  Test provider failures and ensure the UI does not falsely report
    success.
9.  Avoid logging full personal form contents unnecessarily.

**Deliverable:** Tested general and product-specific inquiry workflows.

Do not add credentials or choose a paid provider without approval.

### Phase 6 --- Migration, SEO, and analytics

1.  Build a source-to-destination URL mapping.
2.  Migrate approved company copy, images, product samples, and
    metadata.
3.  Review image rights, accuracy, alt text, and image quality.
4.  Add page-specific metadata, canonical URLs, sitemap, robots rules,
    and social metadata.
5.  Add redirects for changed legacy URLs.
6.  Verify draft/private content is not indexed.
7.  Configure approved analytics and event tracking.
8.  Validate the production domain and search-engine configuration.

**Deliverable:** Approved content migrated, SEO checked, and analytics
configured if authorized.

### Phase 7 --- Quality assurance

Test:

-   All navigation links and calls to action.
-   Mobile menu and responsive breakpoints.
-   Product catalog, filters, search, product pages, and invalid slugs.
-   CMS product create/edit/preview/publish/archive workflow.
-   General and product-specific form validation and delivery.
-   Keyboard navigation, focus visibility, contrast, labels, and errors.
-   Image optimization and layout stability.
-   Metadata, canonical URLs, sitemap, robots, and redirects.
-   Browser console, server logs, and network failures.
-   Production build and type checking.
-   Access control and absence of secrets in client bundles.
-   Representative current browsers and devices.

Use automated tests for critical paths where practical, and perform
manual visual review with real content.

**Deliverable:** QA checklist, resolved launch-blocking defects, and

### Phase 8 --- Deployment and handover

1.  Connect the repository to the approved Vercel account.
2.  Configure preview and production environment variables.
3.  Configure the production domain and HTTPS.
4.  Verify the production database, migrations, media storage, Live
    Preview, and publishing behavior.
5.  Run final smoke tests against the production site.
6.  Confirm backups/export approach for CMS content and asset recovery
    procedures.
7.  Provide CMS instructions and train designated MONIP editors.
8.  Document deployment, environment variables, forms, analytics, and
    routine maintenance.
9.  Confirm ownership of accounts, billing, domain, and credentials.

**Deliverable:** Production website, editor guide, deployment notes, and
handover.

## 6. Environment Variables

Names and placeholders are in `.env.example`. All are server-only.

| Variable | Purpose | Required |
| --- | --- | --- |
| `DATABASE_URL` | Postgres connection string | Always (startup fails without it) |
| `PAYLOAD_SECRET` | Signs admin sessions | Always (startup fails without it) |
| `SITE_URL` | Canonical, sitemap, email, and Live Preview URLs; must match the serving origin | Production (build fails without it) |
| `INQUIRY_NOTIFY_EMAIL` | Receives inquiry notifications (placeholder) | For notifications |
| `BLOB_READ_WRITE_TOKEN` | Vercel Blob media storage | On Vercel (startup fails without it) |
| `RESEND_API_KEY`, `EMAIL_FROM` | Email delivery; without a key, emails print to the console and production inquiries record `emailStatus: failed` | For email delivery |
| `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` | Website chat (server-only). Without both, the chat shows "not available" | For chat |

Analytics ID will be added if a provider is approved. Live Preview needs
no shared secret: it requires a Payload admin session.

Rules:

-   Never commit real secrets.
-   Never prefix privileged tokens with `NEXT_PUBLIC_`.
-   Validate required environment variables at startup or at the
    relevant server boundary.
-   Do not use write-capable tokens for public page rendering.
-   Keep local `.env` files out of version control.

## 7. Testing Strategy

### Unit tests (`pnpm test`, Vitest, 92 tests)

Slugs, catalog URL params (including LIKE wildcard stripping), inquiry
validation, email composition, site URL and indexability, preview path
safety, the publish-state rule for revalidation, and chat request
validation, rate limiting, OpenRouter error mapping (mocked fetch; the
API key is never logged), "Contact us" link rendering, office map
pin positions (cropped view) and label placement, and success story
customer-name approval and date formatting, and grouping categories
under their parent for the admin Categories list, and the AI product
description (input check, prompt, paragraph conversion, free vision model
selection, model fallback), and the Cruise Fleet Schedule (workbook row
parsing and dates at 12:00 UTC, filter queries and month ranges, the Ship
list per cruise line, and the template round trip through the importer).

### End-to-end tests (`pnpm test:e2e`, Playwright, 69 tests)

Run against a production build on port 3100 (can run alongside
`pnpm dev`), using system Chrome and the local development database.
Inquiry tests leave Inquiry records behind (delete
`e2e-*@example.com` inquiries afterwards). Because the tests share the database editors use,
some catalog tests depend on placeholder content and fail once it is
replaced; a separate seeded test database is planned (section 13).
Last run (2026-10-26): 65 passed, 4 catalog filter tests failed on real
content.

-   Catalog browsing, search, category/subcategory filters, empty states.
-   Product and general inquiries, validation errors, honeypot.
-   Home featured products and CMS copy, hero video pause, sticky header,
    header CTA, content and Our clients pages, About offices map and
    list, removed Sustainability page, Privacy policy link, mobile menu.
-   Success Stories: menu link, cards to detail page and back, 404 for
    unknown stories, sitemap entries.
-   Website chat with a mocked `/api/chat`: context, Shift+Enter, state
    across pages, errors, Escape and focus, "Contact us" links, Mike's
    AI label; endpoint rejects system messages and malformed bodies.
-   robots.txt, sitemap, canonical and social metadata, legacy
    `/project-5` redirect.
-   Preview route refusals (no session, unsafe paths); AI description
    endpoint refuses anonymous requests.
-   Cruise Fleet Schedule (creates and deletes `e2e-admin@example.com` and
    `e2e-editor@example.com`): admin-only API and template, filters
    combined with AND and cleared, Ship list narrowed by cruise line,
    empty state, template download with the 13 headers, Import Excel
    (summary, rejected rows, list refresh; the test sailing is deleted)
    and its refusal of non-.xlsx files.
-   axe accessibility scan (WCAG 2.2 AA) of all public pages, plus the
    chat panel open on desktop and mobile.

### Verified manually during development

Access control (anonymous, editor, admin) over REST and GraphQL;
publish, unpublish, and draft leakage on a production build; Live
Preview in the admin; migrations producing the same schema as the dev
database; Lighthouse scores.

### Build gates

Before declaring a task complete, run the repository's relevant:

-   Formatter.
-   Linter.
-   Type checker.
-   Unit/component tests.
-   End-to-end tests when affected.
-   Production build.

Do not claim a check passed unless it was actually run and its result
reviewed.

## 8. Definition of Done

A feature is complete when:

-   It meets the relevant requirement.
-   It follows the established design system and responsive behavior.
-   Loading, empty, success, and error states are handled where
    applicable.
-   It is accessible to the extent appropriate for the feature.
-   It has tests appropriate to risk and complexity.
-   It passes relevant lint, type, test, and build checks.
-   It does not expose secrets or unpublished content.
-   Documentation is updated when setup, environment, CMS, or deployment
    behavior changes.

## 9. Risks and Mitigations

  -----------------------------------------------------------------------
  Risk                                Mitigation
  ----------------------------------- -----------------------------------
  Product data is incomplete          Agree on required fields and
                                      prepare a content import template.

  Brand assets are unavailable        Request approved assets early; use
                                      clearly marked placeholders during
                                      development.

  Legacy URLs lose search value       Inventory URLs and implement
                                      redirects and metadata checks.

  CMS is confusing for staff          Test schemas with a nontechnical
                                      editor and improve labels/help
                                      text.

  Form delivery fails                 Add server-side validation,
                                      provider error handling,
                                      monitoring, and an approved
                                      fallback.

  Sensitive content becomes public    Keep private fields out of public
                                      schemas/queries and test
                                      draft/archive behavior.

  Scope expands during development    Track additions separately and get
                                      approval before expanding launch
                                      scope.

  Production credentials are missing  Identify account owners and access
                                      requirements during Phase 0.
  -----------------------------------------------------------------------

## 14. Known Limitations

-   `notFound()` inside the site (e.g. an unpublished product) returns a
    correct 404 status, but Next.js serves a minimal error shell and the
    branded 404 renders in the browser. This is Next.js behavior for apps
    with multiple root layouts (site + Payload admin). Unmatched URLs use
    `app/global-not-found.tsx` (experimental `globalNotFound` flag) and
    render fully on the server.
-   Lighthouse on localhost reports a 307 "redirect" per page; the
    response is synthesized by Chrome (no server headers), not sent by
    the app.
-   Multi-word catalog searches match only when all words are in the
    same field (name, summary, tags, or materials).
-   Chat rate limiting is in server memory: per instance and reset on restart. Production needs the shared Firewall rule; also set a spending limit on the OpenRouter key.
-   E2E tests run against the shared development database (see section 7).
-   Cruise Fleet Schedule uploads are limited to 4 MB (Vercel's request
    cap is 4.5 MB); larger workbooks, such as the full multi-sheet
    calendar (5.2 MB), go through `pnpm import:sailings`. A full import of
    25,896 new sailings takes about 20 seconds locally.
-   The Cruise Fleet Schedule filter bar shows only its own selections;
    conditions added with Payload's built-in Filters button still apply
    but are not shown in the bar.
-   In development, `payload run` scripts (seed, import) sync the database
    schema to the Payload config first, removing anything added to the
    schema by hand.
-   The developer machine runs Node 24.21.0, slightly below Payload's
    stated minimum (24.22.1); everything works, but upgrading is advised.
