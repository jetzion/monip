# MONIP Group Website Rebuild --- Implementation Plan

**Document:** `PLAN.md`\
**Status:** In progress --- core site built and tested locally;
deployment on hold (last updated 2026-10-22)\
**Companion documents:** `REQUIREMENTS.md`, `CLAUDE.md`, `README.md`,
`Editor_guide_for_MONIP.md`

## 1. Objective

Deliver a modern, responsive, multi-page MONIP Group website using a
custom Next.js frontend and Payload CMS, deployed through
Vercel. The site must provide an easy-to-maintain corporate presence and
a CMS-driven product catalog.

Use `REQUIREMENTS.md` as the functional source of truth. If
implementation reveals a conflict or missing decision, document it and
ask for clarification rather than silently inventing business
requirements.

## 2. Architecture

### Core stack

-   **Next.js 16.4** with App Router; `cacheComponents` disabled because
    Payload does not guarantee full compatibility.
-   **TypeScript** with strict type checking.
-   **Payload CMS 3.91** running inside the Next.js app, admin panel at
    `/admin`. Content is read through Payload's Local API on the server
    with `overrideAccess: false`, so collection access rules always apply.
-   **Postgres**: Docker locally, Neon in production. Schema changes ship
    as migrations in `migrations/`.
-   **Media storage**: local disk in development, Vercel Blob (client
    uploads) in production.
-   **Publishing**: Payload drafts with autosave. Collection hooks call
    `revalidatePath` only when a save changes public content (publish or
    unpublish), not on draft autosaves.
-   **Live Preview**: `/preview` enables Next.js draft mode for logged-in
    Payload users only; drafts are then queried as that user.
-   **Vercel** for preview and production deployment.
-   **Tailwind CSS v4 + shadcn/ui** with design tokens; the visual
    direction is clean and business-professional.
-   **Resend** (via `@payloadcms/email-resend`) for notification and
    auto-reply email.
-   **Vitest** for unit/component tests and **Playwright** for
    end-to-end tests.
-   **pnpm** as the package manager.
-   **Vercel Observability and runtime logs** for basic monitoring.

### Architectural principles

-   Keep the frontend decoupled from CMS presentation templates.
-   Use reusable page templates and components.
-   Fetch public content through narrowly scoped, read-only queries.
-   Use static generation or server rendering where appropriate.
-   Use draft/preview mode only through protected server-side routes.
-   Keep secrets and privileged tokens server-side.
-   Use stable slugs and preserve URL continuity where possible.
-   Payload's Postgres database and admin logins are approved; avoid
    other databases, public authentication, or integrations without an
    approved requirement.

## 4. Data Model

Built: Product, Product Category, Service, Page, Inquiry, Users, Media.
Not built yet: Case Study and Site Settings (waiting for approved
content).

### Product

-   `name` --- required.
-   `slug` --- required and unique.
-   `summary` --- required for cards and previews.
-   `description` --- rich text or structured content.
-   `primaryImage` --- required for publication.
-   `gallery` --- ordered list of uploads; alt text lives on each Media item.
-   `category` --- required reference to a category.
-   `subcategory` --- optional reference to a category whose parent is
    the selected category.
-   `tags` --- optional.
-   `materials` --- optional list.
-   `customizationOptions` --- optional list.
-   `applications` --- optional list.
-   `specifications` --- optional label/value rows (public only).
-   `featured` --- boolean.
-   `labels` --- optional, controlled values.
-   `seo.title` and `seo.description` --- optional with sensible
    fallbacks.
-   Status --- use Payload drafts (`_status`: draft/published) only.
    "Archive" means unpublish; no separate status field.
-   `publishedAt` --- set or maintain consistently.

Do not store supplier details, internal cost, internal notes, or other
confidential information in the CMS at all. Do not expose pricing or
lead-time information unless MONIP explicitly approves it.

### Product Category

-   `title`, `slug`, `description`, `image` (optional), `parent`
    (optional reference; set for subcategories), `sortOrder`,
    `seo.title`, `seo.description`.

### Service

-   `title`, `slug`, `summary`, `body`, `image` (optional), `sortOrder`;
    drafts. Shown as sections on `/services` (no detail pages yet).

### Page

-   `title`, `key` (unique: about, sustainability, privacy), `intro`,
    `image` (optional), `body`, SEO fields; drafts. Each key maps to a route in code.
-   A page, `/services`, and their nav links appear only when published
    content exists; otherwise the route returns 404.

### Case Study (not built)

-   `title`, `slug`, `summary`, `body`, `images`, `clientName` (only
    when approved), `industry` (optional), `results` (only
    substantiated), SEO fields, publication workflow.

### Site Settings (Payload global, not built)

The logo is a static file in code (`public/monip-logo.png`). Footer
content and contact details wait for approved content.


-   Approved logo and brand assets.
-   Navigation configuration if appropriate.
-   Footer content.
-   Approved contact information.
-   Default SEO metadata and social image.

### Inquiry

Written only by the server-side form handler; never queried by public
pages.

-   `type` --- general or product.
-   `name`, `email`, `company` (optional), `phone` (optional),
    `message`.
-   `product` --- reference to the product, plus the product name and URL
    captured at submission time.
-   `createdAt` (submission time, set by Payload).
-   `emailStatus` --- whether the notification email was accepted.

### Users

Payload auth collection for admin panel logins, with `admin` and
`editor` roles. The first account becomes admin; only admins can set
roles.

### Access control

-   Public reads return published Products, Services, and Pages only;
    Categories (no drafts) are always public.
-   Drafts are visible only to logged-in users, including in Live Preview.
-   Inquiries contain personal information: no public read or create,
    no updates by anyone, readable and deletable only by admins. The form
    handler creates them via the Local API on the server.
-   Editors manage content; only admins manage users and read inquiries
    (open question in the editor guide: should editors see inquiries?).

Avoid making every text fragment editable through the CMS. Make business
content editable while keeping structural layout and reusable UI
controlled in code.

## 5. Phased Work Plan

### Approved build order (vertical slice first)

The phases below group the scope. Implementation follows this order:

1.  Minimal shell: design tokens, header, footer, base components.
2.  Product and Category collections in the Payload admin.
3.  Catalog page, product detail page, Live Preview, on-publish
    revalidation.
4.  Product inquiry: save to Payload, notify MONIP, auto-reply,
    success/error states.
5.  Home (with featured products), About, Services, Contact, reusing
    established patterns.
6.  Search and filters, SEO, sitemap, remaining pages.

A few clearly marked placeholder products may be created in Payload for
development; MONIP replaces them through manual entry.

### Phase 0 --- Repository and environment inspection

1.  Inspect the existing repository, package manager, framework,
    branches, and current deployment.
2.  Identify existing brand assets, fonts, images, copy, and any useful
    components.
3.  Inventory current website URLs and content that may need migration.
4.  Identify the current domain/DNS owner and required access.
5.  Confirm Node.js version and deployment constraints.
6.  Record unknowns in a decision log.
7.  Do not delete or replace existing files before understanding their
    purpose.

**Deliverable:** Repository assessment, content inventory, environment
checklist, and decision log.

2.  Confirm primary audience, key messages, calls to action, product
    categories, and contact workflow.
3.  Establish brand tokens: colors, typography, spacing, layout widths,

4.  Define sitemap, responsive navigation, footer, and reusable page
    templates.
5.  Create or implement a small set of representative layouts before

6.  Verify that the design direction works for real MONIP assets.

**Deliverable:** Approved design direction and shared layout/component

### Phase 2 --- Project setup and Payload configuration

## 6. Environment Variables

Names and placeholders are in `.env.example`. All are server-only.

| Variable | Purpose | Required |
| --- | --- | --- |
| `DATABASE_URL` | Postgres connection string | Always (startup fails without it) |
| `PAYLOAD_SECRET` | Signs admin sessions | Always (startup fails without it) |
| `SITE_URL` | Canonical, sitemap, email, and Live Preview URLs; must match the serving origin | Production (build fails without it) |
| `INQUIRY_NOTIFY_EMAIL` | Receives inquiry notifications (placeholder) | For notifications |
| `BLOB_READ_WRITE_TOKEN` | Vercel Blob media storage | On Vercel (startup fails without it) |
| `RESEND_API_KEY`, `EMAIL_FROM` | Email delivery; without a key, emails print to the console and production inquiries record `emailStatus: failed` | For email delivery |

Analytics ID will be added if a provider is approved. Live Preview needs
no shared secret: it requires a Payload admin session.

Rules:

-   Never commit real secrets.
-   Never prefix privileged tokens with `NEXT_PUBLIC_`.
-   Validate required environment variables at startup or at the
    relevant server boundary.
-   Do not use write-capable tokens for public page rendering.
-   Keep local `.env` files out of version control.

## 7. Testing Strategy

### Unit tests (`pnpm test`, Vitest, 35 tests)

Slugs, catalog URL params (including LIKE wildcard stripping), inquiry
validation, email composition, site URL and indexability, preview path
safety, and the publish-state rule for revalidation.

### End-to-end tests (`pnpm test:e2e`, Playwright, 39 tests)

Run against a production build on port 3100 (can run alongside
`pnpm dev`), using system Chrome and the local database with seeded
placeholders. Inquiry tests leave Inquiry records behind.

-   Catalog browsing, search, category/subcategory filters, empty states.
-   Product and general inquiries, validation errors, honeypot.
-   Home featured products, header CTA, content pages, mobile menu.
-   robots.txt, sitemap, canonical and social metadata.
-   Preview route refusals (no session, unsafe paths).
-   axe accessibility scan (WCAG 2.2 AA) of all public pages.

### Verified manually during development

Access control (anonymous, editor, admin) over REST and GraphQL;
publish, unpublish, and draft leakage on a production build; Live
Preview in the admin; migrations producing the same schema as the dev
database; Lighthouse scores.

### Build gates

Before declaring a task complete, run the repository's relevant:

-   Formatter.
-   Linter.
-   Type checker.
-   Unit/component tests.
-   End-to-end tests when affected.
-   Production build.

Do not claim a check passed unless it was actually run and its result
reviewed.

## 8. Definition of Done

A feature is complete when:

-   It meets the relevant requirement.
-   It follows the established design system and responsive behavior.
-   Loading, empty, success, and error states are handled where
    applicable.
-   It is accessible to the extent appropriate for the feature.
-   It has tests appropriate to risk and complexity.
-   It passes relevant lint, type, test, and build checks.
-   It does not expose secrets or unpublished content.
-   Documentation is updated when setup, environment, CMS, or deployment
    behavior changes.

## 14. Known Limitations

-   `notFound()` inside the site (e.g. an unpublished product) returns a
    correct 404 status, but Next.js serves a minimal error shell and the
    branded 404 renders in the browser. This is Next.js behavior for apps
    with multiple root layouts (site + Payload admin). Unmatched URLs use
    `app/global-not-found.tsx` (experimental `globalNotFound` flag) and
    render fully on the server.
-   Lighthouse on localhost reports a 307 "redirect" per page; the
    response is synthesized by Chrome (no server headers), not sent by
    the app.
-   Multi-word catalog searches match only when all words are in the
    same field (name, summary, tags, or materials).
-   The developer machine runs Node 24.21.0, slightly below Payload's
    stated minimum (24.22.1); everything works, but upgrading is advised.
